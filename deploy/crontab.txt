#   - 固定間隔で叩き続ける。時間帯の判定は各コマンドの中で完結する

# メモリの上限（docs/JQUANTS_ARCHIVE.md「メモリ」）。このマシンの実メモリは 11GiB。
# **J-Quants のアーカイブか DuckDB を触るコマンドには全部渡す**——3 つは効く層が違う:
#   JQUANTS_READ_BUDGET_MB … 1 回の読み出しが Go の Frame に載せていい量。超えたら
#                            OOM で殺される代わりに、何を絞れば通るかを書いたエラーで止まる
#   GOMEMLIMIT             … Go のヒープの上限（soft）。ここに近づくと GC が先に頑張る
#   GOGC                   … 上限に余裕があるうちは GC を控える（=速い）。GOMEMLIMIT が天井を守る
#   WBJP_DUCKDB_MEMORY_LIMIT … DuckDB の上限。**Go のヒープの外**なので上の 3 つが届かない。
#                            渡さないとシステムメモリの 80%（9.3GiB）になる。daytrade backtest
#                            （10 年のパネル）は実測 6.5GB で、ここが唯一の柵。超えたら
#                            DuckDB は一時ファイルにスピルするだけで落ちない

# --- 発注経路（立花証券の認証情報を入れたら有効化。まず --live 無しで数日回す）-------------
# ロックは deploy/with-lock.sh で取る（取れずに見送った回もログに残る。flock -n は無言で消える）。
# open / close は 30 秒までロックを待つ——snap が握っていても少し待てば取れる。
# 1 回の実行は execution.max_run_seconds（150 秒）と時間帯の終わりで切れるので、前の回が
# 遅くても次の回は始められる。送れなかった分は次の回が「残りの枚数」として建て直す
#
# 9:00:03・9:00:25・9:01:03・9:03・9:06・9:09・9:13: 気配で並べてロング N・ショートを寄付で建てる。
# 窓は 9:15 まで。前の回が全部建てていれば以降は何もしない（冪等）
# 9:00:25・9:01:03 は初回がすぐ落ちた朝（通信エラー等）の早い再試行。寄った銘柄は遅れるほど高く買い、
# 9:05 に建てると優位がほぼ消える（vault 2026-09-jp-daytrade-minute-entry）ので 9:03 までは待たない。
# 初回や 9:00 の snap（最長 15 秒・打ち切り 18 秒）が長引いてロックを握っていれば 30 秒待って見送る
# （lock_busy。無害で、次の回が拾う）。9:00:25 は初回と 9:00 の snap（約 7 秒。初回の後なら 9:00:16 ごろに終わる）の後に置く
# 2026-09-17 に 9:01 始まりから 9:00:03 始まりへ（vault 2026-09-jp-daytrade-ml-entry-timing）。
# 9:00:00 に寄った銘柄は寄付の直後に上がるので、成行が遅れるほど高く買う（LightGBM の選定は 65% が
# 9:00:00 に寄り、10 秒で始値 +14 bp、65 秒で +19 bp）。3 秒待つのは寄付を時価問合に反映させるため
# （9:00:06 の snap では 9:00:00 台に寄った銘柄の 100% に始値が入っていた。9/16・9/17）。
# 9:13 は us_stale_wait_until（09:12）の後に 1 回回すために残す
# 8:59:45: 寄る前の回（execution.preopen_legs = long）。ここで出した注文だけが**寄成**になり、
# 始値を決める板寄せで建つ。締め切りはコードが 9:00:00（板寄せ）に切る——過ぎてから届く寄成は
# 既に寄った銘柄に約定しないため。実測 4〜9 秒で終わるので 15 秒あれば足りる。
# 送れなかった分は下の 9:00:03 からの回が「残りの枚数」を従来のザラ場の成行で埋める。
# 8:59 の snap は 8:59:35（slot 085935）へ前倒しし、この回にロックを明け渡している
