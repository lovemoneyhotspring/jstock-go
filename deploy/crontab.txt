# 他のジョブ（暗号資産・rcguard）はそのまま。
#
# 方針（docs/DEPLOY.md）:
#   - 固定間隔で叩き続ける。時間帯の判定は各コマンドの中で完結する
#   - 開始の分は互いにずらす（J-Quants のレート制限と、同じファイルへの同時書き込みを避ける）
#   - flock -n で同じジョブの重なりを防ぐ。発注経路（daytrade snap / open / close / verify）は
#     deploy/with-lock.sh 経由——ロックを取れずに見送った回もログに残す
#     open / guard / close / verify は WITH_LOCK_NOTIFY=1——打ち切りと見送りを Discord にも知らせる
#   - --live が無い行は判断と記録だけで注文を出さない（dry-run）
#   - 実行の要約は state/digest/<env>-<日付>.jsonl に 1 行ずつ溜まる（docs/FEEDBACK.md）
#   - 外の死活監視は Mackerel: 9:22 の朝の点検と 15:40 の verify の後に deploy/ping.sh が実行の印
#     （state/ping/<KEY>）を残し、deploy/mackerel-alive.sh が 5 分おきに状態をサービスメトリックへ投稿する。
#     マシン・ネット・cron が止まると通知も全部止まるので、「来なかったら知らせる」のは外のサービスにしか
#     できない（cron 停止は途切れ監視、マシン停止は mackerel-agent の connectivity。docs/DEPLOY.md）
#
# 有効化の段階:
#   1. 2026-09-11〜: データ・候補に加えて、**板の記録（snap）と dry-run の open** を回す。
#      注文は出ない（--live 無し）
#   2. 2026-09-14: 信用口座が開き、信用の発注経路（買建・売建、指値・成行の新規と返済）を
#      本番口座で 1 周させた（docs/BROKER_VERIFY.md）
#   3. 2026-09-15〜: **daytrade の open / close / verify を本番（--live）に切り替え**。dry-run の行は
#      コメントにした。台帳を通した 1 周（verify の「持ち越しなし」）と前営業日の単品照会は
#      本番の初日に確かめる。止めるときは config/daytrade/daytrade.toml の kill_switch = true
#   wbjp / accum の発注経路はまだ開けていない（下のコメント行）。state のバックアップ（accum backup）だけは 2026-09-24 から回す

# メモリの上限（docs/JQUANTS_ARCHIVE.md「メモリ」）。このマシンの実メモリは 11GiB。
# **J-Quants のアーカイブか DuckDB を触るコマンドには全部渡す**——3 つは効く層が違う:
#   JQUANTS_READ_BUDGET_MB … 1 回の読み出しが Go の Frame に載せていい量。超えたら
#                            OOM で殺される代わりに、何を絞れば通るかを書いたエラーで止まる
#   GOMEMLIMIT             … Go のヒープの上限（soft）。ここに近づくと GC が先に頑張る
#   GOGC                   … 上限に余裕があるうちは GC を控える（=速い）。GOMEMLIMIT が天井を守る
#   WBJP_DUCKDB_MEMORY_LIMIT … DuckDB の上限。**Go のヒープの外**なので上の 3 つが届かない。
#                            渡さないとシステムメモリの 80%（9.3GiB）になる。daytrade backtest
#                            （10 年のパネル）は実測 6.5GB で、ここが唯一の柵。超えたら
#                            DuckDB は一時ファイルにスピルするだけで落ちない

# --- 板・気配の記録（docs/OPENING_DATA.md）----------------------------------------
# 発注しない。今の選定はギャップ 1 変数しか見ておらず、「どんな気配なら勝率が上がるか」に
# 答えるデータが無い。板は過去に遡れない（J-Quants の分足にもティックにも板も無い）ので、
# 発注経路を開ける前から溜め始める。1 日止めれば 1 日ぶん永久に欠ける。
# ロックは open / close と**共有**する。時価問合のレート制限（4 回/秒）はプロセス内なので、
# 同時に走ると発注側が弾かれうる。取れなければ snap は何もせずに終わる（発注が優先）。
#
# **開けるのは .env に TACHIBANA_* を入れてから**（`wbjp credentials check` が通ってから）。
# 資格情報が無いと 1 日 10 回、接続失敗のログが溜まるだけになる。発注経路（下のブロック）とは
# 別で、snap は板を読むだけなので**実機検証を待たずに開けてよい**——むしろ発注を開けるまでの
# 期間がそのまま観測期間になる。1 日遅らせれば 1 日ぶん永久に欠ける
# snap は待たない（wait 0）。open / close が握っていれば見送る（発注が優先）。snap 自身は
# book.max_run_seconds（50 秒）で切れる。9:00 台は open の回が 22〜38 秒おきなので、その時間帯の
# snap（8:59:00・8:59:45・9:00:05）は --max-run と WITH_LOCK_TIMEOUT でさらに短く切る。
# snap は open と同じ分に置かない（同時に始まると open が 30 秒待っても取れない日が出る）。
# 9:02・9:05・9:11 は open（9:00・9:03・9:06・9:09・9:13）の間。取れなかったバッチは snap が
# 1 度取り直し、取れた分だけでも記録する。
# 9:00 の回はロックを取る前に 5 秒待つ。9:00:00 に始めると 31 バッチが板寄せの前後に
# またがり、「板寄せの結果」の点にならない（寄り前は 8:59 の回が持つ）。
# 2026-09-17 から open が 9:00:03 に先にロックを握るので、この回だけは 30 秒待つ（発注が優先。
# open が終わってから 9:00:10〜20 ごろに記録する）。open が 30 秒を超えて握れば見送り、ログに残る。
# 既定の 50 秒（book.max_run_seconds）のままだと、初回の open がすぐ落ちた朝にこの snap が
# 9:00:55 までロックを握り、**9:00:25 の再試行を押し出す**。--max-run 15 と打ち切り 18 秒にして、
# 遅くとも 9:00:23 には手放す（記録より発注が優先。2026-09-18 のレビュー）
# 8:59 台（2026-09-18〜）: 寄り直前の気配。8:59 の寄前気配は真のギャップに近く
# （+5% 以上で相関 0.92。9:00 以降の特別気配は約 +2% に潰れる）、寄る前に発注する材料にする。
# 8:59:00 の回も残して、どちらが始値に近いかを同じ日で比べる。対象の銘柄が先に並ぶ（snap.go）。
# 8:59:00 の回だけ打ち切りを短くする——既定の 170 秒だと、接続や書き出しで固まったときに
# 9:01:50 までロックを握り、9:00 台の open 3 回がまとめて見送りになる。
# **--max-run 20 / 打ち切り 25 秒**（2026-09-19 に 35 / 40 から詰めた）。3,682 銘柄でも実測 8〜9 秒で
# 終わるので 20 秒あれば足り、遅くとも 8:59:25 にはロックを手放す——35 / 40 のままだと固まった朝に
# 8:59:40 まで握り、下の 8:59:35 の回（ロック待ち 0 秒）が黙って落ち、8:59:45 の open（待ち 5 秒）の
# 余裕も 5 秒しか残らなかった。切られた回は取れたバッチだけ記録する（全部失うわけではない）。
# 打ち切りの秒数がそのまま上限になる（timeout の -k 10 の猶予まで伸びるのは TERM を握り潰す
# プロセスだけで、snap は既定の動作でその場で終わる。TERM を受けるのは open だけ）。
#
# **2026-09-19 に 8:59:45 の snap（slot 085945）を 8:59:35 と 8:59:55 に割った**——8:59:45 は
# 寄る前の open（寄成）に明け渡したため。どちらも**ロックを待たず（wait 0）、取れなければ
# 何もせず終わる**（発注が優先）。必ず回る保証が無いので morning-check の必須スロットには
# 入れない（deploy/morning-check.sh の EXPECTED_SLOTS）。
#   085935: open の前に滑り込む回。--max-run 8 と WITH_LOCK_TIMEOUT=10 で、固まっても
#           8:59:46〜47 に TERM、死ななくても WITH_LOCK_KILL_AFTER=2 で 8:59:49 までに手放し、8:59:50 の open
#           （DT_PREOPEN_AT。ロック待ち 5 秒）を塞がない。KILL の猶予が既定の 10 秒のままだと 8:59:57 まで握りうる
#   085955: 板寄せの 5 秒前。open（実測 4〜9 秒）の後の回で、取れた日の板は始値にいちばん近い。
#           --max-run 2 と WITH_LOCK_TIMEOUT=4。--max-run は起動とログインの前から測るので問合せに使えるのは 1 秒前後、
