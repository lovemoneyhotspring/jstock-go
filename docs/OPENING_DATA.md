# 寄り付きのデータ（板・分足）を集める

デイトレの選定を「ギャップ 1 変数」から先へ進めるための情報基盤。**これは記録の設計であって、
選定規則を変える提案ではない**。規則を変えるのは、集めたデータで効きが確かめられてから
（`docs/FEEDBACK.md` の改善ループに乗せる）。

## なぜ今すぐ始めるのか

今の選定は 9:00 の時価問合から**ギャップ（寄付 ÷ 前日終値 − 1）1 つ**を作り、昇順に N 銘柄を取る
（`selection.Rank`）。取っている列は `pDOP,pDPP,tDPP:T,pPRP` の 4 つで、板は 1 バイトも見ていない。
「どんな気配なら勝率が上がるか」は、今のデータでは問いとして立てられない。

| データ | 遡れるか | 締切 |
|---|---|---|
| **板・気配の推移** | **不可**。J-Quants の分足にも `O,H,L,C,Vo,Va` しか無く、ティックも約定のみ。板を持つのは立花のリアルタイムだけ | 記録を始めた日から。**1 日遅れれば 1 日ぶん永久に欠ける** |
| **分足** | J-Quants のアドオンで 2 年ぶん | 取り始めた日から 2 年より前は取れない |
| 日足・財務・信用残 | API で 10 年 | 既に溜めている |

記録は発注から独立して動く（原則 1）。板の記録は 2026-09-11 に、発注経路（daytrade の `--live`）は
2026-09-15 に開けた（`deploy/crontab.txt` 冒頭の「有効化の段階」）。発注を開ける前の期間がそのまま観測期間になった。

## 原則

10 年後に「あのとき取っておけば」と言わないための約束。

1. **記録は判断から独立**。記録の失敗が発注を止めない。発注を止めても記録は続く。別コマンド・別 cron・別ロック
2. **取れるものは全部取る**。列を後から足しても過去は埋まらない。容量を見積もった上で広く取る
3. **母集団を絞らない**。今の条件（プライム・売買代金 1 億・時価総額下位 1/3 除外）は 953 銘柄だが、
   条件を変えたくなったときに記録が無いと検証できない。**全上場（約 3,700）を記録する**
4. **1 点でなく時系列**。板寄せの結果 1 点では「気配がどう動いたか」が分からない。寄り前から寄り後まで、
   引けも複数時刻
5. **追記専用・列は増える前提**。1 回 1 ファイルの Parquet（`wbcore/history.Store`）。列が増えても
   `union_by_name` で古いファイルがそのまま読める。訂正は上書きせず新しいファイルで
6. **記録と利用を分ける**。集めることと使うことは別。選定規則は当面変えない

## 段階 1: 板・気配の時系列（最優先。遡れないため）

### 記録するもの

新しい種類 `book` を `state/daytrade/history/book/` に積む。1 行 = 1 銘柄 × 1 観測時刻。

| 群 | 列 | 用途 |
|---|---|---|
| 鍵 | `day`, `run_id`, `recorded_at`（`history.Store` が自動で付ける）, `symbol`, `slot`（`0830` など） | |
| 値段 | 現在値・始値・高値・安値・前日終値（基準値段）・VWAP | ギャップ、寄り後の推移 |
| 出来 | 出来高・売買代金 | 板寄せでどれだけ捌けたか（平時比） |
| 板 | 最良売気配値・最良買気配値とその数量、取れるだけの気配値段階（`pGAP1..` / `pGBP1..` 相当）、売り・買いの総数量 | **需給の偏り**——「一時的な売りか、情報に基づく売りか」を分ける本命 |
| 特別気配 | 気配値種類（特別気配・連続約定気配・ストップ配分など） | 寄り前の板寄せの状態 |
| 時刻 | 現在値時刻 | 鮮度の検査、遅延の検出 |
| 市場 | ETF・指数（`book.extra_symbols`。候補より先に問い合わせる） | 市場全体の地合い。**`plan` は株式だけなので、寄り前の市場の気配はここにしか無い**——ETF は現物なので 8:59 台に板が立つ（指数 `101`/`102`/`151` は寄り前は動かない） |

**立花の時価問合（`CLMMfdsGetMarketPrice`）で実際にどの列名が取れるかは実機で確かめる**。
`sTargetColumn` で列を選ぶ方式なので、取れる列が分かれば追加は列名を足すだけ。確認用に
`daytrade quotes --raw --columns "..."` を用意した（下記「実機で確かめること」）。

### いつ取るか

| 8:59:48〜51.2（寄る前の `open` が撮り始めた時刻。`085949` など。2026-09-28〜） | 候補の**外**の全銘柄の板。寄る前の `open` が候補の気配を取る前に撮る（`--presnap-until`。記録だけ）。候補の板は発注の判断に使った気配（`history/quotes`）にある。2026-09-25 の 1 日だけは独立の snap（8:59:42・`085942`、全銘柄）。それより前は 8:59:40・8:59:43・8:59:35 / 8:59:55 など |

| 15:00 / 15:19 | 引けの板。15:20 成行 vs 引け値、張り付き銘柄に買いが居たか（`margin.carry_penalty` の実測） |

12 時刻（2026-09-24 に 8:59:35・8:59:55 を 1 回にまとめて 13 → 12。いまは 8:59:42）。増やすのは後からできるが、過去は増やせない——迷ったら取る側に倒す。

### 容量とレート

- 3,700 銘柄 × 12 時刻 × 245 日 = **年 1,090 万行**（2026-09-19 に 10 → 13 時刻、9-24 に 12）。
  日足の実績（1,000 万行・299MB、13 列）から列 40 の数値中心で **年 800MB〜1.3GB**、10 年で 8〜13GB
- 分足（段階 2）は実測 **年 1.15GB**（2 年ぶんで 2.3GB）。板と合わせて 10 年で 25GB 前後。
  2026-09-21 時点のディスクの空きは 54GB（99GB 中）。5 年目に見直す
- **2026-09-21 から**: 時価問合は 8 リクエスト/秒、バッチは応答を待たずに 50 ms ずつずらして送る（`marketPriceStagger`）。914 銘柄で 1.14 秒 → 0.55 秒（深夜の実機）。下の所要の見積もりは直列・4 回/秒のときのもの
- （2026-09-20 までの形）時価問合は 120 銘柄/リクエスト・4 リクエスト/秒（`priceLimiter`）。3,700 銘柄 = 31 リクエスト ≒ **8 秒/回**、
  12 時刻で 90 秒/日（寄る前の snap は `--max-run 5` で切るので遅い朝は途中まで）。
  ただし板 40 列 × 120 銘柄の応答サイズは未確認で、大きければバッチを下げる

### 発注と競合させない

レート制限はプロセス内の `sync.OnceValue` なので、`snap` と `open` が同時に走ると**制限を超えて
発注側が弾かれうる**。これは記録が判断を壊す唯一の経路なので塞ぐ。

- `snap` は `open`（9:01 / 9:04 / 9:07）と `close`（15:20 / 15:24 / 15:28）を**避けた時刻**に置く
- それでも重なったときのために `flock -n /tmp/daytrade.lock` を `open` / `close` と**共有**する。
  `snap` は取れなければ何もせず終わる（記録より発注が優先）
- `open` 自身も、受け取った板をそのまま `book` に積む（9:01 の点は `open` が持つ）
- 取れなかったバッチは `snap` が締め切り内で 1 度だけ取り直し（`MarketPricesRawPartial`）、それでも
  取れなければ**取れた分だけ記録**して失敗をログに残す。31 バッチのうち 1 本の失敗で残りを捨てない。
  `open` が使う `MarketPrices` は全バッチが揃わなければ失敗のまま（欠けた気配で発注させない）

### 時刻（2026-09-19 に増やした）

時刻は上の「いつ取るか」の表のとおり。8:57 と 8:59:55（2026-09-24 に寄る前の 1 回へ置き換え、2026-09-25 に寄る前の `open` の中へ畳んだ）と ETF を足した理由は次のとおり（8:57 は 2026-09-25 にやめた）。

**気配と始値のギャップを機械学習で補正する**ための材料集め（vault 2026-09-jp-daytrade-preopen-order）。
本番は寄る前（crontab の `DT_PREOPEN_AT`）の気配で並べて寄成を出すので、その気配が始値からどれだけずれるかを当てられれば
順位付けが直る。8:59:00 の板から始値を当てる試みは R² 0.037 で不発だったが、**時系列の動き**
（気配がどちら向きに・どれだけの速さで動いているか）と**市場全体の地合い**（ETF の気配）は
まだ試していない。そのための ETF（と、2026-09-25 までの 8:57）。時系列の点は 8:59:00・8:59:30・寄る前の `open` の候補の外（8:59:48〜51.2）と発注時の気配（8:59:52）が残る——9/24 の実測では気配が始値に寄るのは寄る直前の十数秒だけだったので、材料はこの 1 分に寄せた。

**8:59:55 は板寄せの 5 秒前**で、寄る前の `open` が終わった後に滑り込む回だった。ただ `--max-run 2` で毎回途中で切れ
（9/24 は 3,698 銘柄中 2,640）、発注の判断にも使えない（もう注文を出した後）ので、2026-09-24 に**発注の前に取り切る
1 回**へ置き換えた（2026-09-25 からは寄る前の `open` の中で候補の外を撮る。`open` の起動は 8:59:48、候補の気配は 8:59:52.2。crontab の `DT_PREOPEN_AT` / `DT_PRESNAP_UNTIL` / `DT_QUOTES_AT`）。「もっと遅く出すべきか」は `open` 自身が残す気配
（`history/quotes`）で測る。

## 段階 3: 何と突き合わせるか

集めた板・分足は、既にある `history/evaluation`（候補全行 × 当日の結果、`rank_group` / `net_bp` 付き）と
`day` × `symbol` で結合できる。「気配の質 → その日の net bp」がそのまま層別できる形になる。

仮説は **「一時的な需給の偏りへの流動性供給」**。これが正しいなら、同じ深さのギャップでも次の軸で
勝率が分かれるはず——分かれなければ仮説が誤りだと分かる。それも収穫。

| 候補変数 | どのデータから |
|---|---|
| 寄り前の売り気配 ÷ 買い気配の数量比 | 板（8:30〜8:59） |
| 8:30 → 9:00 の気配値の推移（下げ続け / 戻し） | 板の時系列 |
| 板寄せの約定数量 ÷ 平時の出来高 | 板 or 分足（`Vo`） |
| 寄り後 1〜5 分の値動きの形 | 分足 |
| 指数連動か個別要因か（TOPIX・同業との乖離） | 日足パネル（既にある） |
| 最良気配のスプレッド（滑りの予測） | 板 |

**判断に使うのは、`evaluate` の蓄積で効きが確かめられてから。** 少なくとも 100 営業日、
できれば 1 年。それまでは記録するだけで、選定規則は今のまま動かす。

2. ~~**応答サイズ**~~ **2026-09-11 に確認済み。** 66 列 × 120 銘柄が 1 リクエストで返り、3,674 銘柄で
   7.3 秒・420KB/回。`MarketPriceBatch`（120）は下げていない
3. ~~**寄り前に気配が返るか**~~ **2026-09-11 に確認済み。`pDPP` は寄り前は空。気配は `pQBP` / `pQAP` に入る。**
   8:59 の全 3674 銘柄で `pDPP`（現在値）も `tDPP:T`（現在値時刻）も**空**、`pQBP` / `pQAP` は全銘柄に
   値があり気配種類は 0107。寄付後も未寄付の銘柄は同じ（9984 は 9:00〜9:05 が始値・現在値とも空で、
   買気配だけが 6710 → 6610 と動き、9:11 に 6410 で寄った）。
   **帰結（当時）: `quotes.Tachibana.Fetch` は寄り前・未寄付の銘柄の値段を取れなかった**——`pDOP` も `pDPP` も
   0 なので `price <= 0` で捨てていた。9:01 の取りこぼし 366/1251（29%）はこれで、しかも落ちているのは
   「寄りが遅れる銘柄」＝ 2026-09-jp-gap-minute の利益源そのもの。
   **2026-09-11 に値段を `pQBP` / `pQAP`（最良気配）から取るように直した**（`quotes.Fetch`、`Quote.FromBook`）。
   ただし板寄せ中の気配は真のギャップを深いほど圧縮する（真の −7% → 観測 +2%）ので、
   `signal.skip_opened` は**開けない結論**（既定 false。`config/daytrade/daytrade.toml` のコメント）
4. ~~**`tDPP:T`（現在値時刻）の寄り前の値**~~ **2026-09-11 に確認済み。寄り前は空。**
   寄付後は「最後に約定した時刻」で、板の時刻ではない（約定の薄い銘柄は板が生きていても古い時刻を返す）。
   秒は返らず分単位（`quotes.MinuteRounding` で補正）。**気配の時刻列は存在しない**ので、
   「板の時刻で鮮度を測る」案は取れない。9:11 の時点で全 3479 銘柄に気配があり、`tDPP:T` で
   古いと判定された 1539 銘柄も全部気配を持つ——**板の有無を鮮度の条件にすると 100% 通る**（検査が無効化される）。
   **2026-09-12 にそれを承知で「板が返っていれば年齢では落とさない」に変えた**（`quotes.Fresh`）。
   理由は、`tDPP:T` で測っていたのが**気配の鮮度ではなく約定の間隔**だったから——落ちていたのは
   約定の薄い銘柄＝寄付が遅れる銘柄＝利益源で、9:04 以降の欠けが 235 → 258 → 274 → 301 と
   増えるのはこれ。板は問い合わせるたびに返る値なので、そもそも測るべき「年齢」を持たない。
   **代償: 立会時間中の `max_quote_age` は板のある銘柄に対して実質効かなくなる。** 残る歯止めは
   遅延気配の印（`Delayed`）と未来時刻の計数（`FutureStamped`）だけ。落ちた銘柄は
   `history/quotes` の `has_book` と構造化ログの `book_kept` で毎日追える
5. **`pIEP`（予想約定値段）は全時間帯で空**（2026-09-11、8:30〜15:19 の全スロットで 0 件）。板寄せ中も入らない

分足について確かめる予定だったこと——一括の配られ方、`Time` が足の開始か終了か、規模——は
2026-09-05 に実機で確認し、`docs/JQUANTS_ARCHIVE.md`「分足（アドオン）」に実測値を残した。
`Time` は**足の開始時刻**（09:00 の足に板寄せの出来高が入る）。
