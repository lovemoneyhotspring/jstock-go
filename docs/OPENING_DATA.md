# 寄り付きのデータ（板・分足）を集める

デイトレの選定を「ギャップ 1 変数」から先へ進めるための情報基盤。**これは記録の設計であって、
選定規則を変える提案ではない**。規則を変えるのは、集めたデータで効きが確かめられてから
（`docs/FEEDBACK.md` の改善ループに乗せる）。

## なぜ今すぐ始めるのか

今の選定は 9:00 の時価問合から**ギャップ（寄付 ÷ 前日終値 − 1）1 つ**を作り、昇順に N 銘柄を取る
（`selection.Rank`）。取っている列は `pDOP,pDPP,tDPP:T,pPRP` の 4 つで、板は 1 バイトも見ていない。
「どんな気配なら勝率が上がるか」は、今のデータでは問いとして立てられない。

| データ | 遡れるか | 締切 |
|---|---|---|
| **板・気配の推移** | **不可**。J-Quants の分足にも `O,H,L,C,Vo,Va` しか無く、ティックも約定のみ。板を持つのは立花のリアルタイムだけ | 記録を始めた日から。**1 日遅れれば 1 日ぶん永久に欠ける** |
| **分足** | J-Quants のアドオンで 2 年ぶん | 取り始めた日から 2 年より前は取れない |
| 日足・財務・信用残 | API で 10 年 | 既に溜めている |

発注経路は今 `deploy/crontab.txt` で止まっている（有効化の段階 1）。**記録だけ先に始めても実運用に
干渉しない**——むしろ発注を開けるまでの期間がそのまま観測期間になる。

## 原則

10 年後に「あのとき取っておけば」と言わないための約束。

1. **記録は判断から独立**。記録の失敗が発注を止めない。発注を止めても記録は続く。別コマンド・別 cron・別ロック
2. **取れるものは全部取る**。列を後から足しても過去は埋まらない。容量を見積もった上で広く取る
3. **母集団を絞らない**。今の条件（プライム・売買代金 1 億・時価総額下位 1/3 除外）は 953 銘柄だが、
   条件を変えたくなったときに記録が無いと検証できない。**全上場（約 3,700）を記録する**
4. **1 点でなく時系列**。板寄せの結果 1 点では「気配がどう動いたか」が分からない。寄り前から寄り後まで、
   引けも複数時刻
5. **追記専用・列は増える前提**。1 回 1 ファイルの Parquet（`wbcore/history.Store`）。列が増えても
   `union_by_name` で古いファイルがそのまま読める。訂正は上書きせず新しいファイルで
6. **記録と利用を分ける**。集めることと使うことは別。選定規則は当面変えない

## 段階 1: 板・気配の時系列（最優先。遡れないため）

### 記録するもの

新しい種類 `book` を `state/daytrade/history/book/` に積む。1 行 = 1 銘柄 × 1 観測時刻。

| 群 | 列 | 用途 |
|---|---|---|
| 鍵 | `day`, `run_id`, `recorded_at`（`history.Store` が自動で付ける）, `symbol`, `slot`（`0830` など） | |
| 値段 | 現在値・始値・高値・安値・前日終値（基準値段）・VWAP | ギャップ、寄り後の推移 |
| 出来 | 出来高・売買代金 | 板寄せでどれだけ捌けたか（平時比） |
| 板 | 最良売気配値・最良買気配値とその数量、取れるだけの気配値段階（`pGAP1..` / `pGBP1..` 相当）、売り・買いの総数量 | **需給の偏り**——「一時的な売りか、情報に基づく売りか」を分ける本命 |
| 特別気配 | 気配値種類（特別気配・連続約定気配・ストップ配分など） | 寄り前の板寄せの状態 |
| 時刻 | 現在値時刻 | 鮮度の検査、遅延の検出 |

**立花の時価問合（`CLMMfdsGetMarketPrice`）で実際にどの列名が取れるかは実機で確かめる**。
`sTargetColumn` で列を選ぶ方式なので、取れる列が分かれば追加は列名を足すだけ。確認用に
`daytrade quotes --raw --columns "..."` を用意した（下記「実機で確かめること」）。

### いつ取るか

| 時刻（JST） | 何を見るための点か |
|---|---|
| 8:30 / 8:45 / 8:55 / 8:59 | 寄り前の気配の推移。「下げ続けたか、戻したか」——ギャップの深さでは見えない情報 |
| 9:00 / 9:02 / 9:05 / 9:10 | 板寄せの結果と、寄り後の初動。**いつ入るのが最適か**の材料 |
| 15:00 / 15:19 | 引けの板。15:20 成行 vs 引け値、張り付き銘柄に買いが居たか（`margin.carry_penalty` の実測） |

10 時刻。増やすのは後からできるが、過去は増やせない——迷ったら取る側に倒す。

### 容量とレート

- 3,700 銘柄 × 10 時刻 × 245 日 = **年 907 万行**。日足の実績（1,000 万行・299MB、13 列）から
  列 40 の数値中心で **年 600MB〜1GB**、10 年で 6〜10GB
- 分足（段階 2）が年 2GB。**10 年で合計 30GB 前後**。現在の空きは 73GB。5 年目に見直す
- 時価問合は 120 銘柄/リクエスト・4 リクエスト/秒（`priceLimiter`）。3,700 銘柄 = 31 リクエスト ≒ **8 秒/回**、
  10 時刻で 80 秒/日。ただし板 40 列 × 120 銘柄の応答サイズは未確認で、大きければバッチを下げる

### 発注と競合させない

レート制限はプロセス内の `sync.OnceValue` なので、`snap` と `open` が同時に走ると**制限を超えて
発注側が弾かれうる**。これは記録が判断を壊す唯一の経路なので塞ぐ。

- `snap` は `open`（9:01 / 9:04 / 9:07）と `close`（15:20 / 15:24 / 15:28）を**避けた時刻**に置く
- それでも重なったときのために `flock -n /tmp/daytrade.lock` を `open` / `close` と**共有**する。
  `snap` は取れなければ何もせず終わる（記録より発注が優先）
- `open` 自身も、受け取った板をそのまま `book` に積む（9:01 の点は `open` が持つ）

### コマンド

```bash
daytrade snap                      # 今この瞬間の板を全上場ぶん記録する（cron が呼ぶ）
daytrade snap --symbols 7203,9984  # 疎通確認
daytrade history book --date 2026-09-08 --csv /tmp/book.csv
```

`--live` は要らない（発注しないため）。失敗はログ（`daytrade.snap`）に残し、終了コードで cron に伝える。

## 段階 2: 分足（2 年で消えるので早く始める）

取り込みは**実装済み**（日付分割・型固定・アドオンは環境変数で opt-in）。設計と使い方は
`docs/JQUANTS_ARCHIVE.md`「分足（アドオン）」。**アドオンは未契約なので、まだ 1 行も入っていない**——
契約して `JQUANTS_MINUTE_BARS=1 jquants backfill --only equities_bars_minute` を回せば、
その時点で遡れる 2 年ぶんが入る。ここでは何のために要るかだけ。

| 問い | 分足で答えられること |
|---|---|
| いつ入るのが最適か | 9:00 の板寄せ / 9:01 / 9:05 / 9:10 の価格を候補全銘柄で比べる。今の「9:01」は cron の都合で決まった値で、検証された値ではない |
| 寄り後の形で選べるか | 9:00〜9:03 で反発を始めた銘柄と下げ続けた銘柄で、大引までの net bp が分かれるか |
| 板寄せの出来高 | 平時比で異常に多い寄り付き（売りが捌けた）とそうでない寄り付きで、その後の戻りが違うか |
| 滑りの実測 | 研究の 5 bp は仮定のまま。粗利 18.9 bp/日に対しコスト 20 bp が損益分岐——ここの実測は成否そのもの |
| 出口 | 15:20 成行 vs 引け値の差、張り付き銘柄が 15:20〜15:30 に出来ていたか |

板が「寄る前の需給」を、分足が「寄った後の値動き」を持つ。**両方揃って初めて寄り付きの戦術を組める**。

## 段階 3: 何と突き合わせるか

集めた板・分足は、既にある `history/evaluation`（候補全行 × 当日の結果、`rank_group` / `net_bp` 付き）と
`day` × `symbol` で結合できる。「気配の質 → その日の net bp」がそのまま層別できる形になる。

仮説は **「一時的な需給の偏りへの流動性供給」**。これが正しいなら、同じ深さのギャップでも次の軸で
勝率が分かれるはず——分かれなければ仮説が誤りだと分かる。それも収穫。

| 候補変数 | どのデータから |
|---|---|
| 寄り前の売り気配 ÷ 買い気配の数量比 | 板（8:30〜8:59） |
| 8:30 → 9:00 の気配値の推移（下げ続け / 戻し） | 板の時系列 |
| 板寄せの約定数量 ÷ 平時の出来高 | 板 or 分足（`Vo`） |
| 寄り後 1〜5 分の値動きの形 | 分足 |
| 指数連動か個別要因か（TOPIX・同業との乖離） | 日足パネル（既にある） |
| 最良気配のスプレッド（滑りの予測） | 板 |

**判断に使うのは、`evaluate` の蓄積で効きが確かめられてから。** 少なくとも 100 営業日、
できれば 1 年。それまでは記録するだけで、選定規則は今のまま動かす。

## 実機で確かめること

1. **時価問合で板の列が取れるか、列名は何か**。`daytrade quotes --raw --columns "pDOP,pDPP,..." 7203`
   で生の応答をそのまま出す。取れた列名を `BookSchema` に確定させる
2. **応答サイズ**。板の全列 × 120 銘柄が 1 リクエストで返るか。返らなければ `MarketPriceBatch` を下げる
3. **寄り前に気配が返るか**。8:30 の時点で `pDPP`（現在値）が前日終値のままなのか、気配値が入るのか。
   ここが空なら寄り前の観測は板の列だけが頼りになる
4. **`tDPP:T`（現在値時刻）の寄り前の値**。`open` が「古い気配」と誤判定した経緯（`docs/DEPLOY.md`）と同じ罠
5. **分足の一括ファイルが日次か月次か**、`Time` が足の開始か終了か（`docs/JQUANTS_ARCHIVE.md`）

## 決めていないこと

1. **板の記録を全上場にするか母集団だけにするか。** 設計は全上場（原則 3）。応答サイズやレートが
   実機で問題になれば、母集団 ∪ 上位 500 に落とす
2. **アドオンの契約時期。** 分足は月額の有料。契約した日から 2 年ぶんが手に入るので早いほどよいが、
   段階 1 が先（板は毎日欠け続けるが、分足は契約すれば 2 年遡れる）
3. **保持期間。** 板は 10 年残す前提で見積もったが、5 年目に容量を見て決める。日足と違い
   「古い板」の価値は薄れる可能性がある
